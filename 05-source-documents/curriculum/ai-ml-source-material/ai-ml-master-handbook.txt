How to Think Out Loud
The single most common failure mode in AI/ML interviews is silence during thinking. Interviewers at top companies explicitly evaluate your reasoning process, not just your answer. Use this protocol:
	•	State your interpretation: "I'm going to treat this as a binary classification problem where..."
	•	State your assumptions: "I'll assume the data is tabular, label noise is low, and latency is under 100ms..."
	•	Enumerate options before committing: "Three approaches come to mind: (1) logistic regression for interpretability, (2) gradient boosting for accuracy, (3) neural net for feature learning..."
	•	Explain elimination: "I'm ruling out deep learning here because the dataset is small (50k rows) and we need fast retraining cycles..."
	•	Choose and justify: "I'd go with gradient boosting because it handles mixed data types, requires minimal preprocessing, and gives feature importance for debugging..."
	•	Proactively add: "The risk is overfitting on the small dataset — I'd use early stopping and cross-validation to mitigate..."

How to Handle Uncertainty in Interviews
	•	Never bluff — interviewers always probe deeper. Say "I'm not certain of the exact formula but the intuition is..."
	•	Show your reasoning process: "I'd approach this by first asking what the business objective is, then..."

	•	Bridge to what you do know: "What I'm confident about is the broader framework — let me explain that and flag where I'd verify specifics..."
	•	After the interview: note gaps and study them — these are signals of your actual weak spots

SECTION 3: Universal Answering Frameworks
Framework 1: MLTD — ML Theory & Design Framework
Use for: Any ML theory, design, or trade-off question. Steps: (1) Problem Frame → (2) Model/Approach Options → (3) Trade-offs → (4) Decision + Justification → (5) Evaluation → (6) Failure Modes → (7) Product Impact
Example: "How would you build a spam classifier?"
	•	Frame: Binary classification. Imbalanced (1-5% spam). Latency sensitive (<50ms). Labels noisy from user reports.
	•	Options: (A) Logistic regression on TF-IDF — fast, interpretable, weak on semantic; (B) Gradient boosting on features — strong baseline, feature engineering needed; (C) BERT-based classifier — best semantic, slow, expensive
	•	Trade-off: Option A best for speed, Option C best for accuracy, Option B best balance
	•	Decision: Start with B, plan C for v2 once infra supports it
	•	Evaluation: Precision@K (minimize false positives = user trust), recall, F1, ROC-AUC, false positive rate as guard metric
	•	Failure modes: Adversarial spam evolution, label drift, training-serving skew on text preprocessing
	•	Product impact: False positive spam = deleted legitimate email = user churn. Weight precision highly.

Framework 2: STAR-T — Behavioral Framework for AI/ML
Use for: All behavioral and project deep-dive questions. STAR-T = Situation, Task, Action, Result, Technical/Product Learning
	•	Situation: Set context — team size, product stage, data constraints, business pressure
	•	Task: What was YOUR specific ownership — not the team's collective goal
	•	Action: Technical and product decisions YOU made with explicit reasoning, not just "we did X"
	•	Result: Quantified impact — model metrics AND business metrics (not just "accuracy improved")
	•	Technical/Product Learning: What you would do differently; what this taught you about the problem class
Framework 3: SCALE — ML System Design Framework
Use for: All ML system design questions. Steps: (S)cope → (C)omponents → (A)lgorithm Choices → (L)atency/Scale/Cost → (E)valuation/Monitoring

Framework 4: PROBE — Debugging & RCA Framework
Use for: Any "model performance dropped", "production issue", "metrics regressed" question. P=Pinpoint, R=Root cause, O=Options, B=Best fix, E=Evaluate fix
	•	Pinpoint: Narrow scope — which metric? Which segment? When did it start? Is it a bug or drift?
	•	Root cause: Hypothesize — data issue? Label issue? Feature pipeline bug? Model degradation? Traffic shift?
	•	Options: Multiple hypotheses, tests to distinguish them
	•	Best fix: Data fix vs model retrain vs serving fix vs threshold change
	•	Evaluate: How do you confirm the fix worked? What metrics monitor going forward?
Framework 5: TRADE — Product Trade-off Framework (AI PM)
Use for: "Should we ship this?" / "What metric should we optimize?" / "What are the risks?" questions.
	•	T = Trade-off articulation: What do we gain vs what do we give up?
	•	R = Risk assessment: What can go wrong? Who is harmed? How reversible?
	•	A = Alternatives: What is the next best option? What does not building this cost?
	•	D = Data/evidence: What do we know? What are we assuming? What would change our decision?
	•	E = Evaluation plan: How do we know if this was the right call? What leading indicators?
Framework 6: LLM-EVAL — Evaluating LLM System Answers
Use for: Any LLM/GenAI design, evaluation, or debugging question.
	•	L = Latency: TTFT, throughput, p99, context length cost
	•	L = Label quality: Is ground truth reliable? What's the annotation rubric?
	•	M = Model quality: Faithfulness, relevance, coherence, groundedness, safety
	•	E = Error analysis: Where does it fail? Systematic vs random errors?
	•	V = Versioning: How do you track changes? Which prompt + model + data combination?
	•	A = Alignment: Does output match the intended use case? Is it safe for deployment?
	•	L = Launch criteria: What is the ship threshold? What guardrails block launch?

ML-Specific Coding Patterns
Pattern 1: Top-K by Frequency (Recommendation / Ranking)
Problem: Given a list of item interactions, return the top-K most interacted items.
Approach: Hash map for counts → Min-heap of size K → Return heap contents.
Complexity: O(N log K) time, O(K) space.
ML connection: Used in candidate generation for recommenders, ranking, beam search.
Pattern 2: Sliding Window (Time Series / Sequential Data)
Problem: Compute rolling average of model predictions over last W steps.
Approach: Maintain running sum, dequeue oldest element, enqueue new.
Complexity: O(N) time, O(W) space.
ML connection: Online learning, streaming feature computation, attention over sequences.
Pattern 3: Matrix Multiplication (Neural Networks)
Problem: Implement forward pass of a single linear layer.
Approach: Y = X @ W + b. Check shapes: (batch, in_features) @ (in_features, out_features) = (batch, out_features).
Complexity: O(batch * in * out).
ML connection: Every linear layer, attention QKV projections, embedding lookups.
Pattern 4: Cosine Similarity (Embedding Search)
Problem: Find top-K similar items to a query embedding from a corpus.
Approach: Normalize all vectors → dot product (= cosine similarity) → argsort descending → return top-K.
Complexity: O(N*D) for brute force; use FAISS/HNSW for large N.
ML connection: RAG retrieval, semantic search, recommendation.
Pattern 5: Batch Processing
Problem: Process a dataset in mini-batches for inference efficiency.
Approach: yield data[i:i+batch_size] for i in range(0, len(data), batch_size).
ML connection: Training loops, batch inference serving, data loading pipelines.

Key Python Idioms for AI/ML Interviews
	•	List comprehensions over loops: [f(x) for x in data if condition] — 2-5x faster in Python
	•	collections.Counter for frequency maps: Counter(items).most_common(K)
	•	heapq.nlargest(K, items, key=lambda x: x[1]) — top-K with custom key
	•	zip(*matrix) for matrix transpose — clean one-liner
	•	enumerate() instead of range(len()) — idiomatic and readable
	•	defaultdict(list) for graph adjacency lists — avoids key existence checks
	•	numpy vectorization: prefer np.dot, np.sum over loops — 100x+ faster
	•	Generator expressions for memory efficiency: (x for x in large_dataset)
Time/Space Complexity Communication Template
Always state complexity before writing code, and confirm after. Use this phrasing:
"Before I code: my approach is O(N log K) time because we iterate once (O(N)) and each heap operation is O(log K). Space is O(K) for the heap and O(N) in the worst case for the hash map. This is efficient for the stated constraints of N=10^6, K=100. Let me now code this up..."

Worked Example 1: 7-Day Retention
Problem: Calculate Day-7 retention rate for each weekly cohort.

WITH first_seen AS (
  SELECT user_id, DATE_TRUNC('week', MIN(event_date)) AS cohort_week
  FROM events GROUP BY user_id
),
day7_active AS (
  SELECT e.user_id, f.cohort_week
  FROM events e JOIN first_seen f ON e.user_id = f.user_id
  WHERE DATEDIFF(e.event_date, f.cohort_week) BETWEEN 6 AND 8
)
SELECT f.cohort_week,
  COUNT(DISTINCT f.user_id) AS cohort_size,
  COUNT(DISTINCT d.user_id) AS day7_retained,
  ROUND(COUNT(DISTINCT d.user_id)*100.0/COUNT(DISTINCT f.user_id),2) AS retention_rate
FROM first_seen f LEFT JOIN day7_active d ON f.user_id=d.user_id
GROUP BY f.cohort_week ORDER BY f.cohort_week;
Worked Example 2: A/B Test Result Analysis
Problem: Compute CTR, conversion rate, and revenue per user for treatment vs control.

SELECT
  experiment_group,
  COUNT(DISTINCT user_id) AS users,
  SUM(clicks) AS total_clicks,
  ROUND(SUM(clicks)*1.0/COUNT(DISTINCT user_id),4) AS ctr,
  SUM(conversions) AS conversions,
  ROUND(SUM(conversions)*1.0/COUNT(DISTINCT user_id),4) AS cvr,
  ROUND(SUM(revenue)/COUNT(DISTINCT user_id),2) AS rev_per_user
FROM experiment_events
WHERE experiment_id = 'exp_2025_q1_homepage'
  AND event_date BETWEEN '2025-01-01' AND '2025-01-14'
GROUP BY experiment_group;
Worked Example 3: Feature Leakage Detection
Problem: Training set for churn prediction might contain post-cancellation events (leakage).

SELECT COUNT(*) AS leaky_rows
FROM training_features f
JOIN user_cancellations c ON f.user_id = c.user_id
WHERE f.feature_date >= c.cancellation_date;
-- If > 0: leakage exists. Fix by filtering f.feature_date < c.cancellation_date
Window Function Patterns
	•	ROW_NUMBER() OVER(PARTITION BY user_id ORDER BY event_date) — session sequencing
	•	LAG(value, 1) OVER(ORDER BY date) — day-over-day change
	•	SUM(revenue) OVER(PARTITION BY user_id ORDER BY date ROWS UNBOUNDED PRECEDING) — cumulative revenue
	•	NTILE(10) OVER(ORDER BY score DESC) — decile bucketing for model score analysis
	•	RANK() vs DENSE_RANK() vs ROW_NUMBER() — know the difference for tiebreaking

6.2 Probability Fundamentals
	•	P(A) — probability of event A; always between 0 and 1; P(sample space) = 1
	•	P(A ∪ B) = P(A) + P(B) - P(A ∩ B) — addition rule; subtract overlap
	•	P(A ∩ B) = P(A) · P(B|A) — multiplication rule; use for joint probabilities
	•	P(A ∩ B) = P(A) · P(B) iff A and B are independent — critical for Naive Bayes
	•	Conditional probability: P(A|B) = P(A ∩ B) / P(B) — "probability of A given B occurred"
	•	Law of Total Probability: P(A) = Σ P(A|Bᵢ)·P(Bᵢ) — marginalize over all cases
Bayes Theorem — Core of AI/ML
P(H|E) = P(E|H) · P(H) / P(E)

Posterior = Likelihood × Prior / Evidence

ML Application: P(spam|words) = P(words|spam)·P(spam) / P(words)
Product Application: P(user churns|usage pattern) = updated belief after observing features

Why it matters for PMs: Every ML model is essentially computing a posterior. Understanding this helps PMs reason about why models are biased toward priors, why rare events are hard to detect, and why calibration matters.

6.4 Hypothesis Testing & Statistical Significance
This is P0 for BOTH engineers and PMs. Wrong statistical inference causes shipping bad features or rejecting good ones.
	•	Null hypothesis (H₀): No effect / no difference (e.g., "treatment = control CTR")
	•	Alternative hypothesis (H₁): There is an effect (e.g., "treatment CTR > control CTR")
	•	p-value: Probability of seeing a result at least this extreme IF H₀ were true. NOT the probability H₀ is true.
	•	α (significance threshold): Typically 0.05. If p < α, reject H₀. Sets false positive rate (Type I error).
	•	Statistical power: Probability of correctly detecting a true effect. Typically want 80-90%.
	•	Sample size: Increases with desired power, decreases with larger effect size, increases with variance
	•	Multiple testing problem: If you test 20 hypotheses with α=0.05, expect 1 false positive by chance. Use Bonferroni correction.
WRONG Interpretation (Causes Bad Launches)
CORRECT Interpretation
"p=0.04 means there is a 4% chance the null is true"
"p=0.04 means: IF null were true, we'd see this result 4% of the time by chance"
"p > 0.05 means the treatment had no effect"
"p > 0.05 means we failed to detect a difference — the effect may still exist but we lack power"
"Our confidence interval is [1.2%, 3.8%] so the true value is 2.5%"
"We are 95% confident the true value falls in [1.2%, 3.8%] — we don't know where in that range"
"We tested 10 metrics and 2 were significant — great!"
"With 10 tests at α=0.05, we expect 0.5 false positives. Apply Bonferroni or pre-specify primary metric."

The fundamental trade-off in ML — one of the most tested topics in any ML interview.

6.6 Calibration
A model is calibrated if its predicted probabilities match empirical frequencies. If the model says "60% chance of click", approximately 60% of those items should actually be clicked.
	•	Why it matters: Uncalibrated probabilities lead to bad decisions in downstream systems (bidding, risk scoring, fraud thresholds)
	•	Calibration plot (reliability diagram): Perfect calibration = diagonal line. S-shaped = overconfident. Flat = underconfident.
	•	Metrics: Expected Calibration Error (ECE), Maximum Calibration Error (MCE)
	•	Fix: Platt scaling (logistic regression on model outputs), isotonic regression, temperature scaling for neural nets
	•	PM relevance: If your fraud model says "90% confidence" but is uncalibrated, your thresholds are meaningless. The whole product decision is wrong.

7.3 Gradient Boosting — Deep Dive (P0 for Engineers)
Gradient boosting is the most commonly used algorithm in industry for tabular data. Understanding its mechanism is required for debugging, tuning, and system design interviews.
	•	Core idea: Fit weak learners (shallow trees) sequentially. Each tree fits the RESIDUALS (gradient of loss) of the previous ensemble.
	•	Prediction: F(x) = f₁(x) + f₂(x) + ... + fₘ(x), each weighted by learning rate η
	•	Loss function: Flexible — use MSE for regression, log loss for classification, custom for ranking
	•	XGBoost improvements over vanilla: L1/L2 regularization on tree weights, approximate split finding, parallel feature evaluation, GPU support
	•	LightGBM improvements: Histogram-based splits (faster), leaf-wise growth (better accuracy), GOSS and EFB for large datasets
	•	Key hyperparameters: learning_rate (η), n_estimators, max_depth, min_samples_leaf, subsample, colsample_bytree
	•	Tuning strategy: Fix n_estimators high, tune tree params, then reduce learning rate and increase n_estimators
PM Relevance: A PM should know that gradient boosting requires more tuning time than random forest, is harder to interpret than logistic regression, but typically gives 2-5% better AUC on tabular data. Use this to set expectations with stakeholders on timeline and interpretability trade-offs.
7.4 Feature Engineering & Label Quality
	•	Feature engineering: Transform raw data into ML-usable representations. Critical for classical ML; less so for deep learning.
	•	Numerical: normalization, log transforms, polynomial features, binning/quantization
	•	Categorical: one-hot, target encoding, frequency encoding, embedding lookups
	•	Temporal: lag features, rolling averages, time-since-event, cyclical encoding (sin/cos for hour-of-day)
	•	Text: TF-IDF, bag-of-words, n-grams, character n-grams for robustness to typos
	•	Label quality: If labels are noisy (30% error rate → model ceiling is ~70% accuracy). Verify via inter-annotator agreement (Cohen's κ).
	•	Label leakage: When features contain information from the future relative to the prediction time. Check: are any features generated AFTER the label event?
7.5 Train/Validation/Test + Cross-Validation
	•	Hold-out split: 60/20/20 or 70/15/15 depending on data size. Never tune on test set.
	•	K-fold cross-validation: K=5 or 10. Average validation metric across folds = better estimate of true performance.
	•	Stratified K-fold: Preserve class proportions in each fold — essential for imbalanced classification.
	•	Time-series split: Respect temporal ordering — train on past, validate on future. Never shuffle time-series data.
	•	Group K-fold: When samples are not independent (e.g., multiple records per user) — group by user to prevent leakage.
	•	Critical mistake: Using validation data to select model, then reporting validation performance as if it were test performance (optimistic bias).

8.2 Learning Rate — The Most Important Hyperparameter
	•	Too high → loss explodes (NaN gradients). Too low → vanishingly slow convergence, local minima traps.
	•	Learning rate warmup: Start small, linearly increase to target LR over first N steps. Essential for transformers.
	•	LR decay schedules: Cosine annealing (smooth decay), linear decay, step decay (reduce by factor every K epochs)
	•	Cyclical LR: Oscillate between min and max LR — helps escape local minima, no manual decay tuning
	•	One-cycle policy: Fast ramp up then gradual decay — achieves good results in fewer epochs
	•	Rule of thumb for LR: 1e-3 for Adam/AdamW with large batches; scale LR ∝ sqrt(batch_size) when scaling batch
8.3 Gradient Descent Variants
	•	Full-batch GD: Gradient over entire dataset per step. Stable but O(N) per update — impractical for large N.
	•	Stochastic GD (SGD): Gradient over 1 sample per step. Noisy but fast updates — good regularization effect.
	•	Mini-batch GD: Gradient over B samples. Best of both — vectorized efficiency, enough noise for regularization. Default B=32-512.
	•	Gradient clipping: Clip gradient norm to threshold (typically 1.0). Prevents exploding gradients in RNNs and transformers.
8.4 Convergence Intuition
Loss landscape analogy: Imagine a hilly terrain. SGD is a ball rolling downhill. High LR = ball bounces around chaotically. Low LR = ball moves slowly. Momentum = ball builds speed going downhill. Adam = adaptive LR per direction based on slope history.
	•	Local minima: Less of a problem for deep networks (empirically). Saddle points are more common and harder.
	•	Sharp vs flat minima: Flat minima generalize better (loss changes slowly with parameter perturbation). AdamW + weight decay tends to find flatter minima.
	•	Loss curves: Monitor both train and validation. If train still decreasing but val plateaus → overfitting. If both plateau early → underfitting or LR too low.
8.5 Weight Initialization
	•	Zero init: BAD — all neurons learn identical features (symmetry breaking problem)
	•	Random init (too large): Signals grow exponentially through layers → exploding activations
	•	Xavier/Glorot init: Scales weights by 1/sqrt(fan_in + fan_out). Good for tanh/sigmoid activations.
	•	He/Kaiming init: Scales by 2/fan_in. Designed for ReLU networks — standard for modern networks.
	•	For transformers: Various schemes depending on depth — often small init (0.02 std) for embedding-level parameters

10.1 Neural Network Foundations
	•	Neuron: y = activation(w·x + b). Weights w learned by gradient descent, bias b shifts the decision boundary.
	•	Layer: Collection of neurons. Deep = many layers. Width = neurons per layer. Depth enables hierarchical feature learning.
	•	Forward pass: Input → hidden layers → output. Each layer: z = Wx + b, a = activation(z).
	•	Backpropagation: Apply chain rule to compute ∂L/∂w for every weight. Gradient = direction of steepest ascent in loss. Update: w ← w - η·∂L/∂w.
	•	Why backprop is efficient: Share computations across paths using dynamic programming (memoization of intermediate gradients).

10.4 Vanishing & Exploding Gradients
Deep networks can have gradients that shrink (vanish) or grow (explode) exponentially as they propagate back through layers.
	•	Vanishing gradients: Gradient = product of many terms <1. Layers near input learn almost nothing. Common with sigmoid/tanh in deep networks.
	•	Exploding gradients: Gradient = product of many terms >1. Loss becomes NaN. Common in RNNs without clipping.
	•	Fixes for vanishing: ReLU activations, residual connections (skip connections), layer norm, LSTM/GRU gates, better init
	•	Fixes for exploding: Gradient clipping (clip norm to max ~1.0), smaller LR, gradient norm monitoring
10.5 Transformer Architecture
The transformer is the dominant architecture for language, vision, multimodal, and increasingly robotics. Understanding it is P0 for all modern AI roles.
	•	Core innovation: Self-attention instead of recurrence. Attention(Q,K,V) = softmax(QKᵀ/√dₖ)·V
	•	Why it works: Each token can attend to ALL other tokens simultaneously — captures long-range dependencies that RNNs struggle with
	•	Multi-head attention: Run attention H times with different learned projections, concatenate outputs → captures different relationship types
	•	Positional encoding: Transformers are permutation-invariant → must inject position info (sinusoidal or learned embeddings)
	•	Feed-forward layers: After attention, each position independently processed through 2-layer MLP. Typically 4x hidden dim expansion.
	•	Layer norm: Applied before (pre-norm, common in modern LLMs like GPT) or after (post-norm, original) each sub-layer
	•	Encoder: Bidirectional attention (BERT-style). Good for classification, understanding. Sees full context.
	•	Decoder: Causal (masked) attention — can only attend to past. Good for generation (GPT-style).
	•	Encoder-decoder: Seq2seq tasks — translation, summarization, question answering (T5-style)

10.7 Transfer Learning
Transfer learning: Use weights pre-trained on large data as starting point for a new task. Most important development in practical deep learning.
	•	Why it works: Lower layers learn general features (edges, textures, syntax). Upper layers learn task-specific features. Fine-tuning adapts upper layers for your task.
	•	Fine-tuning options: (1) Freeze all layers → train only head (few-shot, data-scarce); (2) Freeze lower layers → train upper layers + head; (3) Unfreeze all → full fine-tuning (most data-hungry)
	•	LR for fine-tuning: Use much smaller LR (10x-100x lower) than training from scratch — pre-trained weights are already good, large updates destroy them
	•	Layer-wise LR decay: Common in transformers — lower LR for earlier layers (more general), higher LR for later layers (more task-specific)
PM Relevance: Transfer learning dramatically reduces data and compute requirements. A PM can scope a custom model project 3-5x more feasibly when they understand that "we need 10M labeled examples to train from scratch" becomes "we need 10K examples to fine-tune a pre-trained model".

CSP Fundamentals
	•	Variables: What we're deciding (e.g., which nurse works which shift)
	•	Domains: Possible values for each variable (e.g., {morning, afternoon, night})
	•	Constraints: Rules variables must satisfy (e.g., "no nurse works > 3 consecutive nights")
	•	Solution: Assignment of values to all variables satisfying all constraints
Solving Strategies
	•	Backtracking search: Assign variables one by one, backtrack when constraint violated. Basic but exponential worst case.
	•	Forward checking: When assigning variable, eliminate inconsistent values from neighbors' domains. Prunes search space.
	•	Arc consistency (AC-3): Propagate constraints across all pairs of variables before search. Most powerful pruning.
	•	Heuristics: MRV (minimum remaining values — pick most constrained variable first); LCV (least constraining value first)

Bayes Nets — Practical Intuition
Bayes networks are directed acyclic graphs (DAGs) where nodes are random variables and edges represent conditional dependencies. They compactly represent joint distributions over many variables.
	•	Use case: Medical diagnosis — P(disease | symptoms) decomposed into manageable conditionals via graph structure
	•	Key property: Conditional independence — if X → Y → Z, then X ⊥ Z | Y (Z is independent of X given Y)
	•	Inference: Given observed variables, compute posterior over unobserved. Exact inference is NP-hard in general; use approximate methods (variational, MCMC).
	•	Product relevance: Not directly used as product ML models but shapes how PMs think about dependency between features, model inputs, and decisions

15.3 Collaborative Filtering
	•	User-based CF: Find similar users, recommend what they liked. Problem: scales poorly (O(U²) similarity computation).
	•	Item-based CF: Find similar items, recommend items similar to what user liked. More stable (items change less than users).
	•	Matrix factorization: Decompose user-item matrix into user embeddings × item embeddings. SVD, ALS, SGD variants.
	•	Two-tower model: Separate neural networks for user and item towers. Output embeddings retrieved via ANN (approximate nearest neighbor).
	•	Implicit vs explicit feedback: Clicks/watches (implicit) are easier to collect but noisier. Ratings (explicit) are rare but cleaner. Most modern recommenders use implicit.

16.1 LLM Architecture — What You Must Know
	•	Transformer decoder: Causal self-attention → position-wise FFN → layer norm. GPT-style. Predicts next token.
	•	Context window: Max tokens the model can "see" at once. GPT-4: 128K, Claude 3.5: 200K, Gemini 1.5: 1M. Larger = more expensive.
	•	Tokenization: Text → token IDs via BPE. "unhappiness" → ["un", "happ", "iness"] → [392, 1234, 789]. Tokens ≠ words. ~0.75 words/token for English.
	•	Autoregressive generation: Generate one token at a time. Each new token attends to all previous. O(n²) in context length — critical for latency.
	•	Parameters: GPT-3=175B, LLaMA-3=70B, Gemma-2=27B, GPT-4 estimated ~1T+ mixture-of-experts. More params ≠ better for all tasks.
	•	Scaling laws (Chinchilla): For compute budget C, optimal model size N ∝ √C and training tokens D ∝ √C. Match model size and data.

16.3 RAG — Retrieval-Augmented Generation (P0 for Everyone)
RAG is the most commonly deployed LLM architecture in production. Understanding every component is critical.
RAG Architecture: Query → [Query Encoding] → [Vector Retrieval] → [Context Assembly] → [LLM Generation] → Response

Why RAG? LLMs hallucinate facts. RAG grounds answers in retrieved documents, reducing hallucination and enabling knowledge updates without retraining.
RAG Component Deep-Dive
	•	Chunking: Split documents into chunks for indexing. Chunk size = 256-1024 tokens. Small chunks: precise retrieval, lose context. Large chunks: more context, less precise.
	•	Chunking strategies: Fixed-size, sentence-boundary, paragraph-boundary, semantic chunking (split on topic shifts). Overlap (128 tokens) prevents truncating context at boundaries.
	•	Embedding models: text-embedding-3-large, BGE, E5, all-MiniLM. Choose based on domain, latency, cost. Dimensionality: 384-3072.
	•	Vector databases: Pinecone, Weaviate, Chroma, pgvector, Qdrant. Key: ANN index type (HNSW, IVF), latency, scale, update frequency.
	•	Retrieval: Dense (embedding similarity), sparse (BM25/TF-IDF), hybrid (combine both with RRF). Hybrid typically best.
	•	Reranking: Second-pass reranking of top-K retrieved chunks using cross-encoder (slower but more accurate). ColBERT, Cohere Rerank, Voyage AI.
	•	Context assembly: How to format retrieved chunks + query as LLM prompt. Key: deduplication, relevance ordering, source attribution.
	•	Post-processing: Answer extraction, citation linking, hallucination detection before returning to user.

16.4 Prompting Engineering (P0 for All AI Roles)
	•	System prompt: Sets model behavior, persona, constraints, output format. Critical for production deployment.
	•	Few-shot examples: 3-8 examples in prompt. Choose diverse, representative examples. More examples → better generalization, more tokens.
	•	Chain-of-thought (CoT): "Think step by step" or explicit reasoning instructions. Dramatically improves multi-step reasoning.
	•	ReAct (Reason + Act): Alternate between reasoning steps and tool calls. Foundation of most agent frameworks.
	•	Structured output: JSON mode, XML tags, function calling. Forces consistent parseable output.
	•	Temperature: 0 for deterministic/factual tasks; 0.7 for creative tasks; 1.0+ for diverse sampling.
	•	Prompt injection: Malicious user inputs that override system prompt. Mitigation: input sanitization, separate trust levels, detection classifiers.

16.7 Production LLM Systems — Cost & Latency
Cost drivers: Context length (input tokens), output length, model size (API pricing), inference infrastructure
Latency drivers: Model size, context length, hardware (A100 vs H100), batching strategy, network round-trips
Caching: Cache identical prompts (exact match) or semantically similar prompts (embedding similarity). Can reduce cost 40-60% for repetitive queries.
Model routing: Route simple queries to fast/cheap small model; complex queries to large model. Can maintain quality at 50-70% cost reduction.
Streaming: Stream tokens as generated. Dramatically improves perceived latency (TTFT) even if total latency is same.
Batching: Batch multiple requests together for GPU efficiency. Trades individual latency for throughput.
Quantization: INT8/INT4 instead of FP16 weights. 2-4x memory reduction, modest quality loss. Critical for self-hosted deployment.
PM MUST KNOW: Before launching any LLM feature, answer these 5 questions:
1. What is our hallucination rate on our test set? (must have a number)
2. What happens when the model fails? (designed fallback)
3. What is our cost per query at scale? (unit economics)
4. What is our latency p99? (user experience bar)
5. How do we evaluate quality changes when we update the model or prompt? (regression testing)
16.8 Fine-tuning & RLHF
	•	Supervised Fine-Tuning (SFT): Train on (prompt, ideal response) pairs. Teaches format, style, and domain knowledge.
	•	RLHF overview: (1) Collect human preference data (A is better than B); (2) Train reward model to predict preferences; (3) Use RL (PPO) to optimize policy LM to maximize reward
	•	RLAIF: Replace human annotators with AI annotators (another LLM). Faster, cheaper, but quality depends on AI annotator quality
	•	DPO (Direct Preference Optimization): Bypass reward model and RL. Directly fine-tune on preference pairs with simpler objective. Increasingly popular.
	•	LoRA (Low-Rank Adaptation): Freeze base model weights. Add small trainable matrices (rank 4-64) to attention layers. 10-100x parameter reduction. Standard for efficient fine-tuning.
	•	When NOT to fine-tune: If prompting achieves target quality; if you lack 1K+ high-quality examples; if update frequency is high (retrain cost vs RAG update cost)

17.2 Agent Architecture Patterns
	•	ReAct: Alternate Thought → Action → Observation cycles. Think about what to do, do it, observe result, repeat. Simple and widely used.

	•	Multi-agent: Multiple specialized agents collaborate. One orchestrator agent routes to specialist agents. Parallelizes work but complex to debug.
	•	Tool selection: Agent calls available tools via function calling. Tool catalog must be clear and non-overlapping to avoid confusion.

17.4 Agent Safety & Permissions
	•	Principle of least privilege: Give agent minimum permissions needed for its task. Never give file write access if only read is needed.
	•	Sandboxing: Execute code in isolated containers. Prevent access to host system, network (unless needed), and sensitive files.
	•	Human-in-the-loop (HITL): Require human approval before irreversible actions (send email, delete file, execute payment).
	•	Action audit log: Log every tool call with timestamp, input, and output. Essential for debugging and compliance.
	•	Termination conditions: Always define max steps, max time, and failure conditions. Prevent infinite loops.
	•	Rollback: Design destructive operations to be reversible or require confirmation. "Soft delete" before hard delete.
17.5 Evaluating Agents
Traditional ML metrics don't apply. Agent evaluation requires task-level assessment, not per-step accuracy.
	•	Task success rate: Did the agent complete the goal? Binary or graded. Most important metric.
	•	Step efficiency: How many steps did it take? Fewer steps = more efficient (but not if quality suffers).
	•	Error recovery rate: When agent encounters error, does it recover correctly?
	•	Trajectory quality: Is the sequence of actions reasonable, even if result is correct? (Correct by luck is a risk signal)
	•	Human intervention rate: How often does the agent request help or get overridden? Should decrease over time.
	•	Evaluation methodology: Use diverse, realistic task sets. Not demos. Include adversarial cases, edge cases, and ambiguous instructions.
	•	Trajectory evaluation with LLM-as-judge: Have an LLM evaluate the agent's reasoning chain. Expensive but necessary for complex tasks.

19.1 MDP Fundamentals
	•	MDP (Markov Decision Process): (S, A, T, R, γ) — States, Actions, Transition function, Reward function, Discount factor
	•	Policy π(a|s): Mapping from state to action (or probability distribution over actions)
	•	Value function V^π(s): Expected cumulative discounted reward from state s under policy π
	•	Q-function Q^π(s,a): Expected cumulative reward for taking action a in state s, then following π
	•	Discount factor γ ∈ [0,1]: How much to value future rewards. γ=0 → greedy; γ=0.99 → long-term planning
	•	Bellman equation: V*(s) = max_a [R(s,a) + γ Σ T(s,a,s')V*(s')] — optimal value satisfies this recursive relation

19.3 RLHF — How Modern LLMs Are Trained
RLHF (Reinforcement Learning from Human Feedback) is the post-training step that makes LLMs helpful, harmless, and honest.
	•	Step 1 — SFT: Fine-tune pre-trained LLM on human-written demonstrations of ideal behavior
	•	Step 2 — Reward Model: Collect pairs of model responses + human preferences (A > B). Train a model to predict human preference scores.
	•	Step 3 — RL with PPO: Use the reward model as a reward signal. Optimize LLM policy to maximize reward while staying close to SFT model (KL penalty).
	•	Why KL penalty: Without it, model learns to "game" the reward model (reward hacking). KL divergence keeps policy close to SFT policy.
	•	RLAIF: Replace human preferences with AI preferences. Faster but depends on AI annotator quality.
	•	DPO alternative: Bypasses reward model entirely. Uses preference pairs directly in a simpler loss function. Increasingly standard.
PM INSIGHT on RLHF: The reward model reflects HUMAN ANNOTATOR preferences, not user preferences. Annotators may be biased toward verbose, confident-sounding answers. This is one reason LLMs can sound authoritative while being wrong. PMs must validate that RLHF-trained models match actual user value, not just annotator approval.

21.2 Worked Example: Recommendation System Design
Problem: Design a content recommendation system for a social video app (500M DAU)
SCOPE: Goal = maximize engagement (watch time + retention). Users = 500M DAU. Scale = 5K QPS recommendations. Latency = <100ms p99. Freshness = near-real-time (new videos discoverable within 30 min).
COMPONENTS: User interaction events → Kafka stream → Feature store (user features: interests, history; item features: engagement stats, embeddings) → Candidate generation service → Ranking model → Re-ranking with business rules → Served recommendations → Logging → Offline retraining pipeline.
ALGORITHM — 3-stage funnel:
1. Candidate Generation: Two-tower model (user embedding × video embedding) → top 1000 via ANN (HNSW index on Pinecone). Also BM25 for trending/text-matched content. Output: 1000 candidates.
2. Ranking: LightGBM model on 200+ features (user-video interaction features, user history, video stats). Trained on click + watch time + completion signals. Output: ranked 50 items.
3. Re-ranking: Diversity injection (max 3 videos per creator); freshness boost for new content; promoted content slots; age-gating; user block list filtering. Output: final 20 items.
LATENCY/SCALE: Candidate generation: 30ms (ANN lookup). Ranking: 40ms (LightGBM inference on 1000 items, batched). Re-ranking: 10ms (business rules). Total: ~80ms p99. Cache user embeddings (updated every 1h). Precompute video embeddings offline.
EVALUATION: Offline: NDCG@10, Recall@50 for candidate generation. Online A/B: watch time per session, 7-day retention, skip rate. Guardrail metrics: toxic content rate (<0.01%), creator diversity score. Retraining: daily for ranking model; weekly for two-tower embeddings.
21.3 Worked Example: Fraud Detection System Design
Problem: Design a real-time fraud detection system for a payments platform (50M transactions/day)
SCOPE: Goal = detect fraudulent transactions before settlement. Users = internal risk team + customers. Scale = 600 TPS, burst to 2K TPS. Latency = <50ms (inline with payment processing). Sensitivity: high — fraud loss > false positive cost. Asymmetry: FN (miss fraud) >> FP (false block) cost.
ALGORITHM: Rule-based layer first (fast, interpretable: block if country mismatch + high value + new device), then ML layer. ML model: LightGBM trained on transaction + user + device features. Output: fraud score 0-1. Decision: Block if score>0.9; Review if 0.6-0.9; Allow if <0.6. Label source: human investigators + customer disputes.
DATA CHALLENGES: Label delay (dispute takes 30-90 days → delayed feedback). Class imbalance (0.1% fraud). Adversarial evolution (fraud patterns change). Feature engineering: velocity features (# transactions in last 1h, 24h), device fingerprint, geolocation change distance, merchant category risk score.
MONITORING: Score distribution shift. False positive rate per user segment. Model performance by transaction type. Human review queue depth. Label drift (new fraud patterns). Retraining: weekly with new labeled data. Concept drift triggers: alert if score distribution shifts >2 standard deviations.

23.2 Online vs Offline Metrics — The Critical Gap
The most dangerous assumption in AI product development: "Our offline metrics improved therefore the product is better." This is often WRONG. Always validate offline → online alignment with A/B experiments before trusting offline improvements as product improvements.
	•	Offline metrics: Measured on a fixed held-out dataset. Fast, cheap, reproducible. May not reflect production distribution or user behavior.
	•	Online metrics: Measured in A/B test on live users. Slower, expensive, but captures true user value. The source of truth.
	•	Common offline-online gap causes: Historical data biased toward popular items (popularity bias); evaluation data doesn't match current user distribution; metric doesn't capture user value correctly
	•	Correlation monitoring: Track how well offline metric changes predict online metric changes. If correlation degrades, your offline metric is becoming unreliable.

23.4 Evaluating LLM Systems
No single metric captures LLM quality. Use a multi-layer evaluation framework:
	•	Layer 1 — Automated metrics: ROUGE, BERTScore, exact match. Fast and cheap but low correlation with human judgment.
	•	Layer 2 — LLM-as-judge: Use a stronger LLM (GPT-4, Claude) to score outputs on rubric. Higher correlation with human judgment. Watch for bias toward similar-sounding responses.
	•	Layer 3 — Human evaluation: Gold standard. Expensive and slow. Required for safety, nuanced quality, and preference learning. Use for launch gates.
	•	Evaluation datasets: Must be diverse, representative of production distribution, and regularly updated as product scope changes.
	•	Regression testing: When you update a model or prompt, run your eval set to detect quality regressions. Log prompt + response pairs for future debugging.

	•	Hallucination spike: Check if (1) retrieval changed, (2) prompt changed, (3) model version changed, (4) query distribution shifted. Isolate each component.
	•	Latency regression: Check (1) context length increase (more tokens = slower), (2) model size (routing changed?), (3) infrastructure load, (4) retrieval latency.
	•	Safety/toxicity regression: New model version changed safety behavior? New user segments? Check safety classifier outputs separately from LLM outputs.
	•	Format compliance drop: Prompt changed? Model version changed? Test exact prompt vs model version combinations.
	•	Useful tool: Log every (prompt, response, metadata) tuple. Without logs, LLM debugging is impossible. Implement from day 1.

25.1 Fairness Definitions & Trade-offs
CRITICAL: Different fairness definitions are mathematically incompatible (except in trivial cases). Choosing which fairness criterion to prioritize IS a product decision.
Definition
Mathematical Condition
Appropriate When
Fails When
Demographic Parity
P(Y=1|A=0) = P(Y=1|A=1); Equal positive rate across groups
Goal is equal access regardless of qualification differences
Base rates genuinely differ (e.g., loan default rates differ by income, which correlates with race)
Equalized Odds
Equal TPR and FPR across groups; model equally good for all groups
High stakes; FN or FP costs are high; model quality must be equal
Difficult to achieve when feature distributions differ across groups
Equal Opportunity
Equal TPR across groups; equally detects qualified candidates
High stakes where false negatives (missing qualified candidates) are most costly
May allow different FPR across groups
Calibration
P(Y=1|score=p, A=a) = p for all groups a; scores mean the same across groups
When model output used as probability estimate for downstream decisions
May coexist with disparate impact if base rates differ
Individual Fairness
Similar individuals should receive similar predictions
When explicit group definitions are problematic or when interpersonal consistency is paramount
Requires defining "similar" which is domain-specific and contestable

Impossibility Result (Chouldechova, 2017): When base rates differ between groups, it is mathematically impossible to simultaneously achieve equal positive predictive value, equal false positive rate, and equal false negative rate. A PM must choose which fairness criterion matters most — and defend that choice to stakeholders.
25.2 Bias Sources in AI Systems
	•	Historical bias: Training data reflects past discrimination. Hiring model trained on historical hires → perpetuates historical bias.
	•	Representation bias: Underrepresented groups in training data → poor performance for those groups. Medical imaging AI trained mostly on light skin → worse dermatology for dark skin.
	•	Measurement bias: What is measured differs by group. User engagement data captures behavior of majority users best.
	•	Aggregation bias: Model trained on combined population, deployed on subgroup that differs. Diabetes risk model trained on mixed population deployed on specific ethnic group.
	•	Label bias: Human annotators' biases encoded in labels. Word embeddings amplify gender stereotypes in training text.
	•	Feedback loop bias: Model outputs affect future training data. Low credit scores → fewer loans → less credit history → model scores them lower.

25.4 AI Safety for Products
	•	Harm categories: Content harms (toxic, explicit, self-harm), information harms (misinformation, privacy leaks), economic harms (fraud facilitation), discriminatory harms (unfair treatment)
	•	Safety-by-design: Safety filters and guardrails are not afterthoughts — design them into the system architecture from day 1
	•	Red-teaming: Proactive adversarial testing before launch. Hire adversarial testers to break the system before users do.
	•	Content moderation: Multi-layer approach — pre-generation (classifier on input), post-generation (classifier on output), human review queue for edge cases
	•	Vulnerable user considerations: Design for the most vulnerable user who might use your product. Extra care for: mental health, medical, financial, and children's products
	•	Incident response: Pre-define escalation paths. Who decides to rollback? What is the communication plan? What constitutes a harm threshold?
25.5 User Trust Design
	•	Appropriate reliance: Design for appropriate trust — neither over-reliance (user accepts all AI suggestions without thinking) nor under-reliance (user ignores valuable AI assistance)
	•	Uncertainty communication: Show model confidence where appropriate. "I'm not sure but..." is more trustworthy than false confidence.
	•	Correction flows: Make it easy for users to correct AI errors. Feedback should be easy to give and visibly acted upon.
	•	Appeal mechanisms: For consequential decisions (loan denial, content removal), provide human appeal path.
	•	Transparency: Be clear that users are interacting with AI. Don't deceive users about AI identity (especially in conversational interfaces).
	•	Progressive disclosure: Don't overwhelm users with AI complexity. Show what is relevant, offer more detail on demand.

Cheat Sheet 1: AI Engineer Master Reference
AI ENGINEER — CHEAT SHEET
P0 CODING: Sliding window O(N), heap top-K O(N log K), matrix multiply O(m*n*k). Always state complexity first.
P0 ML THEORY: Bias-variance tradeoff; cross-entropy for classification (not MSE); AUC-ROC for imbalanced; NDCG for ranking
P0 CLASSICAL ML: XGBoost/LightGBM = best tabular baseline. Logistic regression = first interpretable baseline. Always try simple before complex.
P0 DEEP LEARNING: AdamW optimizer standard; He init for ReLU; Layer norm for transformers; Gradient clip at 1.0 for RNNs/transformers
P0 LLM SYSTEMS: RAG > fine-tuning when: knowledge updates frequently; data is scarce; interpretability needed. Fine-tune when: style/format consistency critical; latency tight; data abundant.
P0 RAG: Chunking (256-512 tokens + 128 overlap); hybrid retrieval (dense + BM25); reranking for top-50→top-5; faithfulness check post-generation
P0 AGENTS: Least privilege; HITL for irreversible; max steps + time limits; full action audit log; prefer workflow over agent when task is well-defined
P0 EVALUATION: Offline ≠ Online. Always A/B. Primary metric + guardrails pre-specified. Bonferroni if multiple tests. 2+ weeks for temporal effects.
P0 DEBUGGING (PROBE): Pinpoint → Root cause → Options → Best fix → Evaluate. Check data before blaming model.
P0 SYSTEM DESIGN (SCALE): Scope → Components → Algorithm → Latency/Scale → Evaluation. Never skip Scope.

AI PRODUCT MANAGER — CHEAT SHEET
P0 LLM CAPABILITIES: Context window ≠ memory. Bigger model ≠ better product. Fine-tuning ≠ magic. RAG = best for factual/current knowledge.
P0 BEFORE ANY LLM LAUNCH: (1) Hallucination rate on test set; (2) Designed fallback; (3) Cost/query at scale; (4) Latency p99; (5) Regression test protocol.
P0 METRICS: Pre-specify primary + guardrails before any experiment. Statistical significance ≠ practical significance. Run ≥2 weeks for A/B tests.
P0 FAIRNESS: Fairness definitions are incompatible — must choose which criterion fits your context. Test across demographic groups before launch.
P0 AGENTS: Never ship agents that take irreversible actions without HITL. Start with workflow; graduate to agent when justified.
P0 WHEN NOT TO USE ML: When rules suffice and are interpretable; when data is <1K examples; when compliance requires full explainability; when speed of iteration matters.
P0 RECOMMENDATIONS: 3-stage funnel (candidate gen → ranking → reranking). Cold start = ship blocker if not handled. CTR optimization → clickbait risk.
P1 EXPERIMENTATION: Randomize at user level; pre-specify metrics; never peek; novelty effect fades in weeks 2-3; multiple test correction required.
P1 UNCERTAINTY: Design fallback for low-confidence predictions. Never expose uncalibrated confidence scores to users. Calibrate before thresholding.
P0 RESPONSIBLE AI: Fairness, safety, and explainability are launch criteria, not nice-to-haves. Red-team before ship. Design appeal flows.

Cheat Sheet 3: LLM / GenAI Engineering Reference
LLM / GENAI ENGINEER — CHEAT SHEET
TRANSFORMER: Q,K,V projections → softmax(QKᵀ/√d) · V → multi-head → FFN (4x expansion) → layer norm. Decoder = causal mask.
TOKENIZATION: BPE standard. ~0.75 words/token (English). Token cost ∝ context length. 1M token context = expensive inference.
RAG STACK: Chunking → Embedding → Vector DB (HNSW) → Hybrid retrieval → Reranking → Prompt assembly → Generation → Faithfulness check.
CHUNKING: 256-512 tokens ideal. 128-token overlap. Semantic > fixed for complex docs. Small chunks = precise retrieval, lose context.
FINE-TUNING: LoRA standard (rank 4-64). 10-100x LR reduction vs scratch training. SFT → RLHF/DPO for alignment. DPO simpler than PPO.
PROMPTING: System prompt sets behavior. CoT for reasoning. Structured output (JSON mode). Temperature: 0=deterministic, 0.7=balanced, 1.0+=creative.
HALLUCINATION: Intrinsic (contradicts context) vs extrinsic (adds info not in context). RAG reduces; NLI-based check detects; citation links help users verify.
PRODUCTION: Stream tokens (TTFT). Cache identical prompts. Route simple → small model; complex → large model. Log everything.
AGENTS: ReAct = Thought→Action→Observation. Least privilege. HITL for irreversible. Max steps + timeout. Multi-agent for parallelism.
EVALUATION: ROUGE/BERTScore for automation. LLM-as-judge for quality. Human eval for safety + nuance. Never ship without eval suite.

Cheat Sheet 4: ML Systems & MLOps Reference
ML SYSTEMS & MLOPS — CHEAT SHEET
SYSTEM DESIGN (SCALE): Scope (goal, scale, latency) → Components (data, features, model, serving, monitoring) → Algorithm → Latency/Scale → Evaluation
TRAINING-SERVING SKEW: Use Feature Store; share preprocessing code; shadow mode before deployment; log serving features for comparison.
DEPLOYMENT: Shadow → Canary (1-5%) → A/B test → Staged rollout → Full. Always have rollback plan with pre-defined triggers.
MONITORING: Data drift (PSI, KS), prediction drift, system metrics (latency, errors), business metrics. Alert thresholds: PSI>0.2, latency>SLA, error>0.1%.
RETRAINING TRIGGERS: Metric degradation; significant data drift; scheduled cadence; new data distribution (major events).
FEATURE STORE: Offline (batch, training) vs Online (real-time serving). Consistency between offline and online = prevents training-serving skew.
OFFLINE vs ONLINE: Batch inference for non-latency-sensitive; real-time for user-facing. Consider caching for repeated queries.
EXPERIMENT TRACKING: Log every run: params, metrics, data version, code version, artifacts. MLflow or W&B standard.
BUILD vs BUY: Feature store, model registry, experiment tracking → buy/use OSS. Core ML models → build. Data pipelines → depends on complexity.
COST OPTIMIZATION: GPU utilization target >80%. Quantization (INT8) for inference. Distillation for smaller serving model. Cache popular predictions.

Cheat Sheet 5: Evaluation & Debugging Reference
EVALUATION & DEBUGGING — CHEAT SHEET
CLASSIFICATION METRICS: Accuracy (balanced only); F1 (imbalanced); AUC-ROC (threshold-independent); Precision = TP/(TP+FP); Recall = TP/(TP+FN)
RANKING METRICS: NDCG@K (position-weighted, graded relevance); MRR (rank of first hit); Precision@K (quality of top-K); Recall@K (coverage)
REGRESSION METRICS: RMSE (penalizes outliers); MAE (robust to outliers); MAPE (relative, undefined at 0); R² (variance explained)
A/B TESTING: User-level randomization; pre-specify metrics; 2+ weeks; no peeking; Bonferroni for multiple tests; guardrail metrics mandatory
STATISTICAL MISTAKES: p<0.05 ≠ "large effect"; p>0.05 ≠ "no effect"; CI means 95% of such intervals contain true value, not 95% probability this one does
PROBE (DEBUGGING): Pinpoint (which metric, when, which segment) → Root cause (hypothesis) → Options (tests) → Best fix → Evaluate (confirm)
TRAINING-SERVING SKEW: Log serving features; compare to training distribution; use shared preprocessing code; Feature Store prevents this
LLM DEBUGGING: Isolate retrieval vs generation vs prompt. Log all (prompt, response) pairs. Check faithfulness separately from answer quality.
DRIFT TYPES: Data drift (input distribution shifts); concept drift (input-output relationship changes); label drift (new classes/patterns emerge)
OFFLINE→ONLINE GAP: Offline improvement ≠ online improvement. Always A/B. Monitor offline-online metric correlation over time.
